# Порты: HTTP 200 — ещё не значит, что отвечает ваш сервис

**Для чего:** Когда на машине работает несколько проектов, Claude регулярно попадает в три ловушки: порт занят, после перезапуска работает старая версия, `curl localhost:8000` отвечает 200 — но это чужой сервис. Скилл заставляет проверять, кто на самом деле слушает порт.

**Как использовать:** Создайте .claude/skills/port-management/SKILL.md в проекте или в ~/.claude/skills/ для всех проектов. Claude включит скилл при запуске dev-сервера, бэкенда или docker compose.

```text
---
name: port-management
description: "Правила запуска локальных сервисов. Используй при любом запуске или перезапуске фронтенда, бэкенда, dev-сервера, docker compose: проверь, свободен ли порт, убей старый процесс при перезапуске, убедись, что отвечает именно твой сервис."
---

# Порты

1. Перед запуском проверь порт:
   ss -tlnp | grep ":PORT " || lsof -iTCP:PORT -sTCP:LISTEN -P -n
   - занят чужим процессом → возьми следующий свободный и сообщи об этом;
   - занят старым процессом этого проекта → пункт 2.

2. Перезапуск = убить + проверить + запустить. Повторный npm run dev НЕ убивает старый процесс.
   PID=$(lsof -tiTCP:PORT -sTCP:LISTEN); [ -n "$PID" ] && kill $PID && sleep 1
   Если жив — kill -9. Убедись, что порт свободен, и только потом запускай.
   После трёх неудачных попыток — остановись и скажи пользователю.

3. HTTP 200 ≠ твой сервис. После запуска:
   - lsof / ps: PID и рабочая папка процесса совпадают с проектом;
   - бэкенд: /health возвращает имя и версию сервиса;
   - фронтенд: <title> или <meta name="app-id"> совпадают.

4. Порт сменился → обнови .env и прокси, чтобы фронтенд ходил на верный бэкенд, и скажи пользователю: «бэкенд на :8003 (8000–8002 заняты)». Не хардкодь порты в коде.

5. Держи PORTS.md в корне: сервис → основной порт → запасные.

6. docker compose: порты через ${HOST_PORT:-8000}:8000; перед up — down. down не трогает чужие процессы на тех же портах — их проверяй по пункту 1.
```

**Почему работает:** Ошибка «тестировал старую сборку» самая дорогая: все проверки проходят, но проверяется не тот код. Сверка PID и рабочей папки плюс маркер в /health отличают ваш процесс от чужого, а явное «убить и проверить» закрывает ловушку с повторным npm run dev.

**Когда не работает:** Если сервис работает внутри контейнера, lsof на хосте покажет docker-proxy, а не ваше приложение. Тогда проверяйте через docker ps и /health.
